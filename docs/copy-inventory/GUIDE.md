## 一、先明白一件事：同一句话可能有三份

这是这个仓库最容易踩的坑，也是你最容易白干的地方。

> 📋 **完整名单在 [DUPLICATES.md](DUPLICATES.md)**：16 组重复、「啥都木有~」8 处、「上一次的Cookie刷新失败了…」5 处逐字相同、「加载中」有 5 种写法。改任何一句之前搜一下那份。

**举个真实的例子**：列表空的时候会显示「啥都木有~」。这句话在仓库里有 **5 份**：

| 位置 | 说明 |
| --- | --- |
| `app/src/main/java/com/RobinNotBad/BiliClient/activity/base/RefreshListActivity.kt:25` | 代码里的常量，大多数页面用这份 |
| `app/src/main/res/layout/activity_simple_main_refresh.xml:88` | 布局里直接写死一份 |
| `app/src/main/res/layout/activity_simple_refresh.xml:261` | 同上 |
| `app/src/main/res/layout/fragment_simple_list.xml:25` | 同上 |
| `app/src/main/res/layout/fragment_simple_refresh.xml:26` | 同上 |

你只改代码那一处，**四个布局里的还是旧的**；你只改布局，代码那份还是旧的。有时你会看到「有的页面变了、有的没变」，就是这么来的。

这类「同一句话多个出处」我全查过了，一共 **11 组**，全列在 [05-ui-pages.md](05-ui-pages.md) 的 `U-260`。**动手前建议先扫一眼那份表**，命中就一次全改。

> 所以第 2 步永远是一样的：**先搜，再改。**

## 二、开工五步法

### 第 1 步：从清单里挑一条

打开对应的清单文件（比如改界面文字就是 [05-ui-pages.md](05-ui-pages.md)），挑一条。每条长这样：

```text
### U-014 详情

- **位置**：`activity/message/NoticeActivity.kt:22`
- **出现在哪**：消息页 → 点一条系统通知进详情
- **用途**：告诉用户当前在通知详情页
- **原文**：

> 详情

- **改写**：

```

**「位置」是最重要的**：第一段是文件路径，冒号后面是**行号**。`activity/message/NoticeActivity.kt:22` 的意思是：打开 `app/src/main/java/com/RobinNotBad/BiliClient/activity/message/NoticeActivity.kt`，跳到**第 22 行**附近。

### 第 2 步：把原文整句复制下来

不要只复制一两个字。「加载」这两个字全仓几百处，搜不出来；「加载中，请稍候」只有一处。

### 第 3 步：全仓搜一遍，数命中

用任意编辑器（VS Code、IDEA、甚至记事本的替换窗口）的**全局搜索**：`Ctrl + Shift + F`，粘贴原文，看结果列表。

- **命中 1 处** → 安全，直接改。
- **命中 2 处以上** → 停下来，逐条看：是不是同一句话的多个出处？如果是，**全部都要改**，否则改完不一致。
- **命中 0 处** → 见[常见问题](#九常见问题)第 2 条。

### 第 4 步：按「位置」改

看下文[第四节](#四四种改法各一个真例子)对着做。

### 第 5 步：编译 + 看一眼 + 回填清单

改完**必须编译一次**（见[第八节](#八改完自查)），然后在模拟器或手表上看那个页面。

最后回到清单，把新文案写进「**改写**」那一栏——这份清单同时也是你的进度表。

> ⚠️ **不要一次改 50 条再编译**。改 5~10 条就编译一次。一次改太多，编译失败时你根本不知道是哪条引起的（可能是 3 处同时错）。这是仓库 `AGENTS.md` 里「小步提交」的由来。

## 三、怎么判断这条该改哪个文件

清单的「位置」已经告诉你文件了，但你还要知道**它属于哪一种**，因为改法完全不同。看文件后缀就够：

```text
位置里的路径以 .xml 结尾
├─ 在 res/values/      → 字符串资源 → 改法 A（第四节 4.1）
└─ 在 res/layout/      → 界面布局   → 改法 C（第四节 4.3）

位置里的路径以 .kt 或 .java 结尾 → 代码 → 改法 B（第四节 4.2）
                                └─ 但如果是 tutorial/Tutorials.kt → 改法 D（第四节 4.4），
                                   它虽然也是 .kt，但有特殊排版规则
```

对照表：

| 你在清单里看到的位置 | 属于 | 改哪 | 难度 |
| --- | --- | --- | --- |
| `app/src/main/res/values/strings.xml:129` | 字符串资源 | 改 `<string>` 标签中间的文字 | ⭐ |
| `app/src/main/res/layout/xxx.xml:72` | 布局 | 改 `android:text="..."` 引号里的字 | ⭐ |
| `app/src/main/java/.../XxxActivity.kt:38` | 代码 | 改双引号里的字 | ⭐⭐ |
| `app/src/main/java/.../tutorial/Tutorials.kt:54` | 教程正文 | 改 `text("...")` 里的字，且**要升版本号** | ⭐⭐⭐ |

**为什么有四种而不是一种？** 这四种是 26.10.19 文案集中化**之前**的历史形态。集中化之后，绝大多数文案已经是 `strings.xml` 里的一行（Kotlin 侧是 `UiText.of("…")` 或 `getString(R.string.…)`，布局侧是 `@string/…`），所以**现在的默认改法是「只改 `strings.xml` 的值」**；只有下面这些还留在代码里：`const val`、`when`/`==` 里当键用的比较、`api/ApiErrorText.kt` 的错误码映射、日志与异常文本、`tools:text`。判断口诀与完整清单见 [`STRINGS-MIGRATION.md`](STRINGS-MIGRATION.md) §4 与 §9。

## 四、四种改法（各一个真例子）

### 4.1 字符串资源 `res/values/strings.xml`

文件开头长这样（第 2 行）：

```xml
<resources xmlns:tools="http://schemas.android.com/tools">
    <string name="app_name">RE：哔哩终端</string>
    <string name="about_description">轻量的第三方B站客户端</string>
```

**只改 `>` 和 `<` 中间的字**：

```xml
<!-- 改之前 -->
<string name="about_description">轻量的第三方B站客户端</string>
<!-- 改之后 -->
<string name="about_description">轻巧的第三方哔哩哔哩客户端</string>
      ↑ 这个 name 一个字都不能动
```

**这个文件有 5 条特有的规矩：**

1. **换行写 `\n`，不能真按回车。** 例如 `strings.xml:5` 的 `about_say` 里是 `...\n最低兼容安卓7.0\n...`。
2. **单引号要写成 `\'`。** 文件里 `Don\'t` 这种写法（`:92`、`:120`、`:121`）就是这个原因。中文引号 `「」`「『』」不用转义。
3. **`<` 和 `>` 要包起来。** 看 `strings.xml:291-292`：`<![CDATA[<]]>`、`<![CDATA[>]]>`。正文里直接写 `<` 会让 XML 解析失败。
4. **`#` 不是注释。** `strings.xml:16` 那行 `# 旧的免责声明` 和 `:297` 的 `#新增功能放到上面…`，是**裸文本**，AAPT 只是容忍它才没报错。你要写注释请用 `<!-- -->`。**别学它们的样子加 `#`。**
5. **数组里的 `<item>` 是正文，不是注释。** `strings.xml:80` 开始的 `#投稿者：…`、`#来源：…` **会原样显示给用户**。

**数组特别提醒**：文件里有 5 个 `<string-array>` —— `eggs`（`:77-124`）、`icon_license`（`:188`）、`update_log_items`（`:298-347`）、`update_log_current`（`:350-363`）、`update_history_log`（`:366-554`）；另有 10 个 `<array name="tutorial_*">`（`:627-674`，旧教程链路用的）。它们都用 `<item>…</item>` 装内容：

- 加一条 = 加一对完整的 `<item></item>`；删一条 = 删掉整对。
- **留一个空的 `<item></item>`**：在 `update_log_items`（`:300`）里它是**当空行用的，别删**；在历史日志数组里它是「清空该组」的手段（读取时被跳过）；换到别的数组可能显示成一个空行。
- 这些数组的 `<item>` 之间**不留注释**，因为一旦注释没配对，整个数组会解析失败。

### 4.2 代码里的硬编码（`.kt` / `.java`）

```kotlin
// 改之前  NoticeActivity.kt:22
setPageName("详情")

// 改之后
setPageName("通知详情")
```

**只改双引号里**。函数名、括号、逗号全都不碰。

**三个坑：**

1. **一句话被拆成几段拼起来的**，会分布在同一行或相邻行：

   ```kotlin
   setPageName("缓存" + folder.name)      // 只改「缓存」两个字
   String.format(Locale.getDefault(), "已阅(%ds)", 3)   // 别动 %d
   ```

2. **带占位符的字符串**（`%s`、`%d`）**数量、顺序、字母都不能变**，否则运行时崩溃或显示乱码。`strings.xml` 里带占位符的一共 7 条：

   | 行号 | name | 原文 |
   | --- | --- | --- |
   | `:49` | `text_update` | `下载的APK保存在: %s\n\n…` |
   | `:55` | `text_update_download_failed` | `下载失败：%s` |
   | `:60` | `text_update_new_found` | `发现新版本 %s` |
   | `:589` | `feedback_ok` | `已收到，反馈编号：%1$d\n感谢你的反馈！` |
   | `:590` | `feedback_fail` | `发送失败：%1$s` |
   | `:618` | `tutorial_pager` | `…（共有%d页，…）` |
   | `:293` | `percent` | `%`（这条其实没人用，别管） |

   改这几个时，`%s` / `%d` / `%1$d` 原样留在句子里就行，位置可以挪（`新版本 %s 已发布` 也合法），但**不能删、不能增、不能把 `%d` 写成 `%s`**（数字用 `%d`，文字用 `%s`）。

   > 代码里也有同类占位符，只是换了形式，两种都要当心：
   >
   > - **`String.format` 式**：`tutorial/TutorialPagerActivity.kt:213` → `String.format(Locale.getDefault(), "已阅(%ds)", …)`。`%d` 不能动。
   > - **字符串拼接式**：`activity/message/MessageActivity.kt:142-143` →
   >   `"回复我的" + (if ((stats.getInt("reply") > 0)) ("(" + stats.getInt("reply") + "未读)") else "")`
   >   这里「回复我的」和「未读」是可改的文字，括号和 `stats.getInt("reply")` 不能碰。
   >   ⚠️ 这条正好又是「双真相」：`activity_message.xml:105` 还写死了一份「回复我的」，改的话两处一起改。

3. **`if / else` 两个分支各有一份文案**，改一个忘另一个。清单里标了「双真相」的优先查。

### 4.3 界面布局 `res/layout/*.xml`

```xml
<!-- 改之前  activity_simple_refresh.xml:72 -->
<TextView android:text="全部" ... />

<!-- 改之后 -->
<TextView android:text="全部视频" ... />
```

**三种要分辨的写法：**

| 你会看到 | 怎么办 |
| --- | --- |
| `android:text="全部"` | 直接改引号里的字 ✅ |
| `android:text="@string/pagename_message"` | **改这里没用**，要去 `strings.xml` 找 `pagename_message` 改 ↩️ |
| `tools:text="正在加载…"` | **不要改**，这是设计预览，不进 APK ❌ |

`android:hint="..."`（输入框灰字提示）和上面完全一样。`android:contentDescription="..."` 是**给读屏软件念的**，不是屏幕上的字，但也要改（全仓只有 4 处，见 05 的 §0.4）。

**一个容易撞上的坑**：文字如果以 `@` 或 `?` 开头，必须写成 `\@` / `\?`，否则 Android 会把它当成「资源引用」去别处找，编译报错。真实例子：`activity_message.xml:158` 写的是 `android:text="\@我"`——那个反斜杠是**必须的**，别当成手滑删掉。

### 4.4 教程正文 `tutorial/Tutorials.kt`（最难，单独说）

这个文件不是普通代码，它用一种「逐段拼接」的写法，**每段文字单独调用一次 `text()`，后面跟着样式**。真实例子（`Tutorials.kt:53-62`，推荐页教程）：

```kotlin
page {
    text("欢迎来到推荐页面").bold().color(HIGHLIGHT)   // 标题：粉色加粗
    newline()
    newline()                                          // 空一行
    text("顶栏").bold().color(ACCENT)                  // 小标题：蓝色加粗
    text("：")                                          // 普通冒号
    text("点击").bold().color(ACCENT)                   // 操作词：蓝色加粗
    text("可以返回上一页或打开菜单，")
    text("整个顶栏都能点").bold()                        // 普通加粗强调
    text("，不必一直费劲地点左上角。")
    newline()
    ...
}
```

**所以你改文字时必须遵守：**

- 只改 `text("…")` 括号**里面**的字，`text(` `)` `.bold()` `.color(...)` 一律不动。
- ⚠️ **不要把相邻的几段合并成一句**。上面「顶栏：点击可以返回上一页…」这四段是拆开的，因为中间有蓝色加粗。合并成一句就**全变成白字**，样式没了。
- 一句话里的某个词要强调，就再拆一段出去。
- `newline()` 是换行，**两个 `newline()` 是空一行**（排版约定写在 `Tutorials.kt:25-32` 的文件头注释里）。删了行距会挤成一坨。
- 列表项用 `"· "` 开头（不是 `-`、不是 `*`）。

**最要紧的一条：改完正文必须把这一篇的 `version` 加 1。**

```kotlin
val recommend = tutorial(
    id = "recommend",
    title = "推荐页面-重要教程",
    version = 1,          // ← 改成 2
    ...
)
```

原因：用户是否看过这篇，是按「上次看过的版本号」判断的（`tutorial/TutorialStore.kt:14` 那句 `readVersion(id) >= tutorial.version`）。**版本号不变，老用户永远看不到你改后的版本**——他们会一直看到旧的那份，或者干脆不再弹出。改了字忘了升版本，等于这次白改。

## 五、十条红线：碰到会出事

| # | 不能做的事 | 后果 |
| --- | --- | --- |
| 1 | 改 `strings.xml` 里的 `name="..."` | 全工程所有引用它的地方编译失败：`Unresolved reference: R.string.xxx` |
| 2 | 在 `strings.xml` 里用 `#` 当注释 | 那不是注释。要注释用 `<!-- -->` |
| 3 | 把还在用的 `<string>` 用 `<!-- -->` 注释掉 | 编译失败（还在被引用） |
| 4 | 删 / 改 / 增 `%s`、`%d`、`%1$d` | 运行时崩溃或显示成 `%s` 原文 |
| 5 | 改三处对外承诺却不同步 | 老用户看不到新的隐私说明（见下） |
| 6 | 改教程正文不把 `version` 加 1 | 老用户永远看不到新版 |
| 7 | 改更新日志的固定格式 | 更新日志页整组消失（见下） |
| 8 | 把教程里分散的 `text()` 合并成一段 | 丢掉加粗/变色，变成一坨白字 |
| 9 | 改 `tools:text` 或 `tools:` 开头的任何属性 | 白改，那只是编辑器里的预览 |
| 10 | 改清单第 14 节的设计占位符，或第 15 节的死字符串 | 白改：前者运行时被接口数据覆盖，后者全文无人引用，用户永远看不到 |

### 红线 5：三处必须一起改的承诺

这三句是**互相对外承诺**的，改一句必须三句一起改，而且还要动一个版本号：

| 编号 | 位置 | 是什么 |
| --- | --- | --- |
| `A-028` | `strings.xml:17` `about_to_uncle` | 免责声明长文 |
| `A-030` | `strings.xml:25` `text_setup_introduction` | 首次启动引导长文 |
| `A-036` | `strings.xml` `privacy_consent_message` 等 5 条 | 启动时的隐私弹窗 |

改完还要把 `app/src/main/java/com/RobinNotBad/BiliClient/api/TerminalApi.java:85-86` 的 `PRIVACY_VERSION` **加 1**。不加的话，已经同意过的老用户不会再看到新的隐私弹窗——而你现在改的内容正是需要他们重新确认的。这三处的同步要求，在 `strings.xml:562-566`、`TerminalApi.java:85-86`、`util/TelemetryReporter.kt:15` 三处源码注释里都写了，别只改文案不看注释。

### 红线 7：更新日志的固定格式

更新日志页不是简单显示文字，它靠正则表达式**从文字里抠版本号**。所以：

| 规则 | 谁在检查 |
| --- | --- |
| `update_log_current` 第一行必须是 `【YY.MM.DD 本次更新】` | `activity/settings/UpdateHistoryActivity.kt:40`、`:54-55` 用 `\d{2}\.\d{2}\.\d{2}` 抠版本号，抠不到就显示异常 |
| 历史日志每组第一行必须是 `## YYYY-MM-DD` | `:94` 靠开头的 `##` 加一个空格分组，没有前缀整组不显示 |
| `[分类]` 首尾方括号必须保留 | `:202` 会把方括号连同中间的字一起加粗，删了方括号就只剩普通字 |
| 不能出现重名日期组 | `:96-103` 重名整组丢弃 |
| 空的 `<item></item>` | `:74`、`:92` 会被跳过（这是清空某组的手段，不是 bug） |

另外：**这个数组不要留自定义占位行**。发版时 `update_log_current` 会被整段搬进 `update_history_log`，占位行会一起搬过去。

## 六、两个完整示范（从清单到改完）

### 示范 A：改一个设置项的说明文字

**清单条目**（[04-settings.md:1514](04-settings.md#L1514) 的 `S-121`，节选）：

```text
### S-121 条目说明「界面大小」

- **位置**：`app/src/main/res/values/strings.xml:21`（`R.string.desc_setting_ui`）
- **出现在哪**：设置 → 界面与外观 → 「界面大小」下方灰色说明
- **控件类型**：说明文字（长段落，两行 + 警告）
- **用途**：给出安全范围与「别乱调」的警告

> 有效范围为0.25~5.00（倍），建议每次仅进行轻微调节，调节后请预览页面，确认显示正常后完成修改，打开新页面后将会生效。

```

> 04 的条目比别家多一行「**控件类型**」（说明文字 / 开关 / 单选 / 跳转），因为设置项点击后的行为不同。

**动手：**

1. 复制原文开头一段 `有效范围为0.25~5.00（倍）`
2. 全局搜索，命中 1 处（`strings.xml:21`）→ 安全
3. 打开 `strings.xml` 第 21 行，改 `>` 和 `<` 中间的字
4. 保留句中的 `\n`（原文里「生效。」和「注意：」之间那个换行，源码里写作 `\n`）；保留 `0.25~5.00` 这类**数值**——它和真实功能绑定，改了会误导用户（别的说明里的 `30`、`72` 同理）
5. 编译
6. 进「设置 → 界面与外观 → 界面大小」看效果
7. 回填清单的「改写」栏

## 七、手表小屏的字数常识

这个应用主要跑在手表上（`AGENTS.md`：一切功能优先考虑手表端），屏幕比手机小得多。以下不是硬限制，是经验值：

| 位置 | 建议上限 | 超了会怎样 |
| --- | --- | --- |
| 顶栏页面标题 | **6 个汉字** | 被 `…` 截断，用户看不出这是哪页 |
| Toast / Snackbar 提示 | **14 个汉字** | 短的只显示约 2 秒，长的也读不完就跑 |
| 列表项名称 | **8 个汉字** | 挤成两行或截断 |
| 设置项说明 | **前 12 字最重要** | 说明文字可长，但只有开头会被扫到 |
| 弹窗正文 | **4 行以内** | 要滚动才看得全 |

另外两个小毛病，改的时候**顺手统一**就好，别专门去改：

- 省略号有两种写法混用：`...`（三个点）和 `…`（一个省略号字符）。清单 05 的「存疑」里记了具体位置。
- 「共1张图片」「共 1 张图片」这种数字前后要不要空格，全仓也不统一。

## 八、改完自查

打勾，一项一项来：

- [ ] 全局搜**旧原文**，确认没有残留（除非那条本来就是故意的双真相，那就确认每一处都改了）
- [ ] 编译通过（见下）
- [ ] 进那个页面亲眼看一眼（尤其确认**没有被 `…` 截断**）
- [ ] 如果改了教程正文 → **`version` 加 1 了吗**
- [ ] 如果改了三处承诺之一 → **三处都改了吗，`PRIVACY_VERSION` 加 1 了吗**
- [ ] 如果改了更新日志 → **首行 `【YY.MM.DD 本次更新】` 还在吗，`[分类]` 方括号还在吗**
- [ ] 回清单，把新文案填进「改写」栏

**编译命令**（在仓库根目录，Windows 下用 `gradlew.bat`）：

```bash
./gradlew.bat :app:assembleDebug
```

看到 `BUILD SUCCESSFUL` 就通过。如果报 `Unresolved reference: R.string.xxx`，说明你把某个 `name` 改了或注释掉了（红线 1、3）。

⚠️ **改了 `res/` 下的文件名或增删了资源文件时，编译可能骗你**——缓存会回放旧结果，报一个明明存在的东西「找不到」。症状和修法写在 [`docs/agents/build.md`](../agents/build.md) 的「build cache 回放陈旧资源」：先 `:app:clean`，再 `assembleDebug`，**分两次运行**，并且带上 `--offline --no-build-cache --no-configuration-cache`。

## 九、常见问题

**1. 我改了，但界面上没变。**

按可能性从高到低查：

- 你改的是 `tools:text` → 白改（红线 9），改 `android:text`
- 你改的是布局，但代码在运行时又 `setText` 覆盖了 → 搜代码里有没有同名赋值
- 你改的是 `@string/xxx` 那个引用本身 → 要去 `strings.xml` 改
- 缓存没刷新 → `:app:clean` 后重编

**2. 我在清单里看到的原文，全局搜搜不到。**

三种原因：

- 原文里有 `\n`（换行），界面上显示成两行，你复制的是显示出来的样子 → 搜**前半句**试试
- 原文在代码里是拼起来的（`"前缀" + 变量 + "后缀"`）→ 搜没有变量的那半段
- 原文在 `strings.xml` 的数组 `<item>` 里，被 `#投稿者：` 之类的行首标记包着 → 搜中间一段

**3. 中文显示成乱码。**

编辑器编码没设成 **UTF-8**。改成 UTF-8 重新打开。别用「另存为 GBK」去救，会越救越乱。

**4. 我想确认某句到底会不会显示给用户。**

两个办法：① 看清单的「出现在哪」，写清了触发路径；② 如果它是 `strings.xml` 里的，搜一下它的 `name` 有没有被引用——**没被引用的就是死字符串**（比如 `update_tip`、`update_log_items` 全仓无人引用，改了也没人看见）。清单 05 的第十五节专门列了这些死字符串。

**5. 一次改多少合适？**

5~10 条，编译一次。同一个页面的文案一起改（这样只需进一次页面验证）。跨文件的大改按「一个页面一轮」切。

**6. 改完要不要更新 `docs/FEATURES.md` 或更新日志？**

如果是纯措辞调整（意思没变）→ 不用。如果**用户能看到的行为或说法变了**（比如「缓存」改叫「下载」）→ 要更新 `docs/FEATURES.md`；`AGENTS.md` 的规矩是新增用户可见功能才动它，措辞微调不算。

## 十一、把新文案交给我（怎么配合）

你负责「写中文」，我负责「搬进代码」。**位置已经在清单里预留好了**，你不用碰任何源码。

### 11.1 写在哪

**原文已经替你抄进「改写」位了**（2026-10-19 起）。你打开任何一条，看到的就是：

```text

- **原文**：添加成功
- **改写**：添加成功

```

原文较长时（多行）：

```text

- **原文**：

> 当前客户端版本较低，可能无法正常播放，建议更新到最新版本。

- **改写**：

> 当前客户端版本较低，可能无法正常播放，建议更新到最新版本。
```

两种情况改法一样——**直接改「改写」那份，原文那句留着别动**（原文是我日后核对与批量替换的锚点，删了我就不知道你要替换哪一句）：

- 短文案（一行）→ 改冒号后面的字：`- **改写**：添加成功` → `- **改写**：收藏好了`
- 长文案（引用块）→ 就地改 `>` 里的字，行数增删随意
- 暂时不想改的写 `（保持原样）`，别留空——留空我分不清「还没写」还是「故意删成空」

**要换行**的（比如带 `\n` 的长说明），一段一行写，我按行还原成 `\n`：

```text

- **改写**：

有效范围为0.25~5.00（倍）。
注意：不要调到最值处！
```

### 11.2 写完打个标记，我一眼看出哪条待办

把该条**标题**末尾加上 `〔待落地〕`：

```text
### U-014 详情 〔待落地〕
```

我改完源码后，会把它换成落地位置：

```text
### U-014 详情 〔已落地：activity/message/NoticeActivity.kt:22〕
```

于是你随时全文搜 `〔待落地〕` 就知道还剩多少条没做——这就是你的进度条。

### 11.3 一次给几条都行

不用等整份清单写完。**5~10 条一轮**最稳（见 8.2）：一轮里我可以顺手查双真相、查格式陷阱，出问题也只影响这一小批。

### 11.4 我拿到之后会做什么

1. 按「位置」打开源码文件，先确认原文还在——**对不上会回来问你，不瞎猜**
2. 把原文换成你写的字，**只搬字，不改你的措辞**
3. 顺手体检：有没有「双真相」漏改、`%s`/`%d` 有没有丢、有没有以 `@` 开头、要不要同步 `strings.xml` 的其它份
4. 回填清单：填 `改写` 栏 + 标记换成 `〔已落地：…〕`
5. 汇报「改了哪几个文件、哪几行、有没有需要你确认的地方」

### 11.5 两件我干不了、得你来的事

- **编译验证**：本机命令行可正常构建（实测 `./gradlew.bat :app:assembleDebug` → `BUILD SUCCESSFUL`，两个 flavor × 4 个 ABI）。所以落地后**由我跑** `assembleDebug` 与 `:app:testStandardDebugUnitTest` 并把结果贴出来，你只需看效果。
- **真机看效果**：手表小屏会不会截断（第七节），只有装上去才知道。

### 11.6 我可能会打回的三种情况

| 情况 | 我会怎么做 |
| --- | --- |
| 你写的句子里少了 `%s` / `%d` | 直接告诉你少了，等你补（擅自补会词不达意） |
| 新文案以 `@` 或 `?` 开头 | 自动加 `\` 转义（XML 里会被当资源引用），并在汇报里说明 |

## 十二、觉得 1000 多条太多？四条省力路线

1012 条逐条手写，谁也写不完。按「省力程度」从高到低排——四条可以叠加。

### 12.1 只定规则，让 Lead 批量替换（最推荐）

**你不用逐条写，只写一张替换规则表**：

| 旧 | 新 | 适用范围 |
| --- | --- | --- |
| `操作失败` | `没成功` | 全局 |
| `加载失败` | `没加载出来` | 只改长提示，Toast 不动 |
| `请稍后再试` | `等会儿再试` | 全局 |

Lead 按这张表在全仓替换，然后回一份报告：每条命中几处、落在哪几个文件、哪些位置被判断为**不该替换**（注释、`tools:text` 预览值、技术字符串）。[DUPLICATES.md](DUPLICATES.md) 那 94 组重复大部分能被一次覆盖——它们的成因本来就是同一句话散在多处。

> 规则表写法：一行一条，旧文案在前、新文案在后。同类尽量合并成一条（如「所有 `xxx失败` 统一去掉『请』」），命中越多越划算。

### 12.2 按「语气」定原则，而不是按条目写字

先定 3~5 条全局原则，例如：

- 错误提示一律「发生了什么 + 你可以怎么办」，不说「操作失败」这种空话；
- 「喵」只保留在彩蛋与登录欢迎，功能提示里不出现；
- 按钮一律 2~4 字，不用「请点击」；
- 空状态一律「没有 X」+ 一句引导，不堆感叹号。

Lead 按原则把全仓**不符合**的句子列出来，你只做「这条同意 / 这条保留」的勾选，不用自己写字。03（教程）与 06（提示）最适合这么处理。

### 12.3 只改高频可见的

用户天天看到的是四类：**通知栏 / 错误 Toast / 空状态 / 首次启动**。`desc_*` 长说明、关于页条款、冷门设置项，一辈子点不了两次。

可以让 Lead 先给每份清单标「高频 / 低频」，你只改高频那 100~200 条，其余保持原样——**不写也是合法状态**，清单不会因此报错。

### 12.4 治本：把文案收进 `strings.xml`（一次性工程）

现在代码里有 2991 条中文字面量，同一句话散在多处。收进资源文件后，改文案只改一处，也能被 `resConfigs 'zh'` 统一管理。

代价是改动面大、要逐处验证（见 `八、改完自查`）。**可以只做「94 组重复 + 43 处 `strings.xml` 撞车」这一批**——范围明确、收益最直接，不必一次全收。

> 顺序建议：先用 12.1 吃掉重复，再用 12.3 精修高频，12.4 留给以后有整块时间时做。
